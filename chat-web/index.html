O PC fica atrás do roteador, então o site não consegue chamar o PC. Por isso quem abre a conexão é o agente no PC. Nenhuma porta do PC fica exposta na internet, e a política de segurança (rover_mcp_safe) continua rodando no PC: mesmo que o site fosse comprometido, ele só conseguiria pedir as 5 tools abaixo, nunca /cmd_vel.

As 5 tools dedicadas

Elas substituem as tools genéricas do ros-mcp que confundiam o modelo (ver ROS-MCP, seção “Falhas do teste com LLM”).

ToolO que faz
navigate_to(x, y, yaw_deg, timeout_s)pausa o explore, manda o goal ao Nav2, espera o fim e responde ARRIVED / ABORTED / CANCELED / TIMEOUT, com a posição final e a distância até o alvo. Recusa alvos a mais de 30 m.
run_mission(steps, on_failure)executa até 12 passos em ordem (go_to, move_forward, wait, return_to_base) e responde MISSION COMPLETE ou MISSION FAILED com uma linha por passo. Para no primeiro passo que falhar (ou volta para a base com on_failure="return_to_base"). O stop_navigation interrompe a missão.
stop_navigation()pausa o explore e cancela todos os goals do Nav2, inclusive os do explore_lite
set_exploration(enabled)liga/desliga o explore_lite
get_robot_pose()posição no frame map, calculada pelo /tf (map→odom→base_link)

Os perfis do rover_mcp_safe.py (--profile ou ROVER_MCP_PROFILE) são:

  • nav (padrão): as 5 tools mais as de leitura.
  • minimal: só as 5 tools. É o perfil usado pelo chat web.
  • full: inclui as escritas genéricas antigas, só para depuração.

O botão PARAR da página chama stop_navigation direto, sem passar pelo LLM, e funciona mesmo enquanto um navigate_to está esperando.

Montar (uma vez)

  1. Chave grátis do Groq: crie uma conta em console.groq.com → API Keys → Create API Key. Não pede cartão. O modelo padrão é o openai/gpt-oss-120b (o llama-3.3-70b-versatile foi desligado pelo Groq em 16/08/2026). Para trocar de provedor, mude LLM_BASE_URL/LLM_MODEL (qualquer API compatível com OpenAI serve, por exemplo Gemini ou OpenRouter).
  2. Render: crie uma conta em render.com com o GitHub → New → Blueprint → escolha o repositório ros2_nav2. O render.yaml da raiz cria o serviço rover-chat (plano free). Ele pede:
    • LLM_API_KEY: a chave do Groq;
    • CHAT_PASSWORD: a senha da página (invente uma);
    • AGENT_TOKEN: é gerado automaticamente. Copie em Environment para usar no PC.
  3. A URL fica algo como https://rover-chat-xxxx.onrender.com.

Usar (toda vez)

# 1) simulação (container) — explore:=false para a IA comandar sem disputa
docker start rover_mcp
docker exec -it rover_mcp bash
ros2 launch rover_bringup rover_mcp_sim.launch.py \
  slam:=true explore:=false headless:=true launch_rviz:=false sim_lite:=true

# 2) agente (host, outro terminal) — espere o /odom existir (~1 min)
cd ~/Documentos/ros2_nav2
~/.local/share/pipx/venvs/ros-mcp/bin/python -I tools/rover_web/agent.py \
  --server wss://rover-chat-xxxx.onrender.com --token 'COLE_O_AGENT_TOKEN'
# deve imprimir: connected to wss://... with tools: get_robot_pose, navigate_to, ...

Depois abra a URL no navegador (funciona no celular também), digite a senha e mande ordens: “onde você está?”, “vá para x=2, y=0”, “ative a exploração”, “pare”.

Para parar tudo: docker stop rover_mcp.

Com a interface gráfica (Gazebo + RViz)

Para ver o rover se mover enquanto conversa com ele, troque o passo 1 por:

xhost +SI:localuser:root          # libera o X para o root do container (vale até deslogar)
docker start rover_mcp
docker exec -it -e DISPLAY=:1 -e QT_X11_NO_MITSHM=1 rover_mcp bash
source /opt/ros/jazzy/setup.bash && source /root/ros2_ws/install/setup.bash
ros2 launch rover_bringup rover_mcp_sim.launch.py \
  slam:=true explore:=false headless:=false launch_rviz:=true sim_lite:=true

O container usa --net=host, então ele alcança o socket do X do desktop sem montar /tmp/.X11-unix. Confira o número do display com echo $DISPLAY no host (aqui é :1). Sem GPU, o Gazebo renderiza pela CPU, e a simulação fica mais lenta que no modo headless. Se pesar demais, use headless:=true launch_rviz:=true: o RViz é bem mais leve e já mostra o mapa, a pose e o caminho do Nav2. Se a janela do Gazebo ficar preta, entre no container também com -e LIBGL_ALWAYS_SOFTWARE=1.

Teste local, sem Render

PY=~/.local/share/pipx/venvs/ros-mcp/bin/python
LLM_API_KEY=... AGENT_TOKEN=t CHAT_PASSWORD=p $PY -I tools/rover_web/server.py   # http://localhost:8000
$PY -I tools/rover_web/agent.py --server ws://127.0.0.1:8000 --token t

Sem chave do Groq, dá para usar o Ollama local, que tem API compatível: LLM_BASE_URL=http://127.0.0.1:11434/v1 LLM_MODEL=llama3.2 LLM_API_KEY=x. Sem GPU, porém, ele leva cerca de 1,5 min por resposta.

Limites e armadilhas

  • O Render free dorme depois de cerca de 15 min sem acesso, e acordar leva cerca de 1 min. O agente faz um ping a cada 10 min e se reconecta sozinho, com espera crescente.
  • A cota do Groq free é limitada por minuto e por dia. Se estourar, a página mostra “the free LLM quota is exhausted”. Espere e tente de novo.
  • Um agente por vez: um agente novo derruba o anterior.
  • Uma simulação por vez. Duas simulações ao mesmo tempo (por exemplo, uma headless esquecida e uma nova com GUI) publicam no mesmo /clock. O tempo da simulação “volta” (Detected jump back in time no log), e o EKF (robot_localization) diverge para NaN, sem se recuperar. As tools passam a responder LOCALIZATION BROKEN, e o LLM avisa que é preciso reiniciar a simulação. A solução é docker restart rover_mcp, que mata tudo, e subir uma única simulação. Para conferir antes de lançar: docker exec rover_mcp pgrep -a gz.
  • Reinicie o agent.py depois de atualizar o código. Ele carrega o rover_mcp_safe só ao iniciar.
  • model_not_found (404) no chat quase sempre é erro de digitação em LLM_MODEL no dashboard do Render (por exemplo, um ponto final colado junto: openai/gpt-oss-120b.). O valor do dashboard tem prioridade sobre o padrão do código. Confira em /health, no campo model.
  • Distâncias longas demoram. A simulação roda a ~0,4× o tempo real: 6 m levam cerca de 1,5 min, e 10 m passam de 5 min. O navigate_to espera até 600 s por padrão (ROVER_MCP_NAV_TIMEOUT).

Navegação no terreno lunar (perfil uneven_terrain)

O moon.world é só um heightmap, sem pedras. O lidar 2D fica a ~0,21 m do chão, então qualquer rampa suave à frente (~2,4° a 5 m) virava “parede” no /map do SLAM, e o Nav2 planejava em cima disso. O resultado eram abortos com “Start occupied” (o rover passava por cima de uma parede fantasma) e “exceeded maximum iterations”.

Correções (rover_navigation/launch/bringup.launch.py, rover_bt.xml):

  • Costmap global feito pelo /scan, e não pelo /map. O raytracing vai até 5 m (inf conta como livre), mas só retornos a menos de 0,8 m (~15° de inclinação) viram obstáculo. A área sob o rover é sempre limpa. O SLAM continua só para localização.
  • Costmap local de 6×6 m. O RPP só segue os pontos do caminho dentro dele; com 3×3 m, um desvio de 1,5 m gerava “Resulting plan has 0 poses”.
  • Behavior tree: replaneja a cada 3 s a partir da pose atual e faz até 4 novas tentativas, limpando os costmaps e esperando. Sem BackUp/Spin.
  • O perfil vem ligado por padrão no gazebo.launch.py e no rover_mcp_sim.launch.py (uneven_terrain:=false desliga). No bringup.launch.py, usado pelo robô real, o padrão é false, porque lá as paredes existem.

Bateria de 7 goals (quadrado de 3 m, volta à origem, 6 m e 10 m):

ConfiguraçãoChegaramFalhas
original~1“Start occupied”, “max iterations”
+ costmap global pelo /scan4/7“plan has 0 poses” (controller)
+ BT com replanejamento + costmap local 6 m6/71 timeout a 0,9 m do alvo de 10 m (limite antigo de 300 s)
